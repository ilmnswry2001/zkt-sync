# تشخيص مشكلة تجمّد تقرير الشركة في Lovable Cloud

## الخلاصة

المشكلة ليست في وجود خطأ واحد داخل واجهة التقرير فقط. النمط الذي ظهر في المشروع يجمع بين ثلاثة أسباب: تحميل بيانات أكثر من اللازم في المتصفح، تنفيذ تجميع وعرض داخل React بدل قاعدة البيانات، وعدم وجود وصول مباشر إلى قاعدة Lovable Cloud للتحقق من مخطط قاعدة البيانات وتطبيق فهارس أو دوال آمنة. هذا يفسر ظهور صفحة غير مستجيبة، ثم ظهور أخطاء Schema Cache عند استخدام دالة لم تُطبّق.

## ما وجدته في الحالات المشابهة

توضح مناقشة Supabase الرسمية المرتبطة بمشاريع Lovable Cloud أن قاعدة البيانات التي ينشئها Lovable Cloud تُدار بواسطة Lovable ولا تظهر عادةً في حساب Supabase الشخصي. لذلك فإن محاولة فتح مشروع Supabase خارجي أو تشغيل SQL من حساب Supabase لن تعالج قاعدة المشروع الفعلية [1].

توثق Supabase أن نتائج `select` لها حد افتراضي، وأن استخدام `range` أو `limit` ضروري لتجنب نقل حمولة كبيرة إلى المتصفح. كما توصي الوثائق باستخدام pagination عندما تكون البيانات كبيرة [2].

توضح وثائق PostgREST أن التصفية والحدود تُرسل عبر نطاقات HTTP، وأن الاستعلامات يجب أن تستخدم فلاتر وفهارس مناسبة. عدم تقييد الاستعلام يعني أن طبقة API قد تنقل مجموعة أكبر من المطلوب حتى لو كانت الواجهة تعرض جزءًا صغيرًا منها [3].

تؤكد وثائق Supabase أن الفهرس يسرّع البحث في الأعمدة المستخدمة في شروط `where`، وأن غياب الفهرس يؤدي إلى مسح كامل للجدول عند نمو البيانات [4]. في هذا المشروع، الأعمدة الأكثر أهمية هي `site_daily_reports.report_date` و`site_daily_reports.site_id` و`site_daily_report_lines.report_id`.

أما من جهة الواجهة، فتوضح وثائق TanStack Virtual أن القوائم الكبيرة ينبغي أن تعرض العناصر المرئية فقط بدل إنشاء عناصر DOM لكل الصفوف. هذا حل مناسب إذا كان المطلوب عرض تفاصيل كثيرة، لكنه ليس الحل الأول للتقرير الحالي لأن التقرير المطلوب هو لوحة مؤشرات يومية [5].

## الخيارات المقترحة

| الخيار | الفكرة | الميزة | المخاطرة أو القيد |
|---|---|---|---|
| أ. لوحة يومية محدودة | جلب رؤوس تقارير يوم واحد ثم جلب بنود تلك الرؤوس فقط، ثم عرض بطاقات إحصائيات ومخططات مختصرة | أقل تغيير، سريع، ولا يحتاج دالة SQL جديدة | يعتمد على فهارس وقواعد وصول صحيحة |
| ب. View أو RPC في قاعدة البيانات | إنشاء View أو دالة تجمع الأرقام داخل PostgreSQL ثم تعيد صفوفًا قليلة للواجهة | الأفضل أداءً عند تضخم البيانات | يحتاج تطبيق Migration داخل Lovable Cloud، وهو غير متاح لنا من لوحة Supabase الخارجية |
| ج. Edge Function داخل Lovable Cloud | نقل التجميع إلى وظيفة خادم مع تحقق من المستخدم وإرجاع DTO صغير | يفصل منطق التقرير عن المتصفح ويتيح مراقبة الأخطاء | يحتاج إعدادًا وإدارة إضافية داخل Lovable |
| د. نقل المشروع إلى Supabase مملوك للمستخدم | إنشاء مشروع Supabase خاص ثم ترحيل المخطط والبيانات وربط Lovable به | سيطرة كاملة على SQL والفهارس والسجلات | عملية ترحيل مستقلة وتتطلب خطة نسخ احتياطي واختبار |
| هـ. Virtualization | إبقاء تفاصيل كثيرة لكن عرض العناصر المرئية فقط | مناسب للجدول الضخم | لا يعالج استعلامًا يحمّل بيانات ضخمة ولا يحل عدم مزامنة المخطط |

## التوصية

أوصي بالبدء بالخيار **أ** كحل تشغيلي مباشر، مع تصميم الواجهة كلوحة مؤشرات لا كجدول نصي. يجب أن يكون الاستعلام محصورًا بيوم واحد، وأن يُنفّذ على مرحلتين كما في شاشة إدخال التقرير اليومية: جلب رؤوس تقارير اليوم، ثم جلب البنود باستخدام `in(report_id, ...)`. بعد ذلك تُحسب الإحصائيات الصغيرة محليًا من هذه النتائج المحدودة.

يجب أن تتضمن اللوحة بطاقات لإجمالي العاملين، إجمالي الآليات، الآليات العاملة، الآليات المتوقفة، المواقع التي أرسلت تقاريرها، ونسبة الإنجاز. ويمكن إضافة مخططين صغيرين لتوزيع العاملين والآليات، مع قائمة مختصرة للمواقع التي لم ترسل تقرير اليوم. لا ينبغي عرض كل التفاصيل في DOM دفعة واحدة.

بعد استقرار الخيار **أ**، يكون الخيار **ب** هو التحسين الدائم إذا كان Lovable Cloud يسمح بتطبيق Migration داخل بيئته. عندها يُنقل التجميع إلى PostgreSQL، وتصبح الواجهة مستهلكة لنتيجة صغيرة فقط. إذا استمر عدم الوصول إلى قاعدة Lovable أو ظهرت أخطاء مزامنة، فالخيار **د** هو المسار الاستراتيجي، وليس ترقيع استعلامات الواجهة باستمرار.

## ضوابط تمنع تكرار المشكلة

يجب منع أي استعلام بلا تاريخ أو بلا `limit`. ويجب ألا تُستخدم دالة RPC جديدة قبل اختبار وجودها في البيئة المستهدفة. كما يجب فصل استعلام رؤوس التقارير عن استعلام البنود، وإضافة فهرس مركب على تاريخ التقرير والموقع، وفهرس على `report_id` في جدول البنود إذا كان ذلك متاحًا داخل Lovable Cloud.

قبل كل نشر، ينبغي اختبار أربع حالات: يوم بلا تقارير، يوم بتقرير واحد، يوم بعدة مواقع، وفترة بيانات كبيرة لا تتجاوز يومًا واحدًا. كما يجب إظهار حالة تحميل غير حاجبة للصفحة ورسالة خطأ قابلة للفهم بدل ترك المتصفح ينتظر حتى يظهر `Page Unresponsive`.

## القرار المطلوب قبل التنفيذ

أقترح اعتماد الخيار **أ** الآن، مع إبقاء الخيار **ب** كتحسين لاحق بعد التأكد من طريقة تطبيق Migration في Lovable Cloud. لن أنفذ نقلًا إلى Supabase مستقل أو تغييرًا في قاعدة البيانات أو الصلاحيات قبل موافقة منفصلة لأن ذلك يغيّر ملكية البنية التحتية ويحتاج خطة ترحيل ونسخ احتياطي.
